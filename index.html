The method: flaw, control, repair, retest

A test that passes proves nothing unless the same test can fail. So every film first reproduces the failure, then proves the detector can see it, then applies the smallest repair and repeats the identical check.

Why the control matters

The control asserts the flaw is observable. If a bug test cannot fail, a green run is silence, not evidence. This is also the quickest review step for AI-generated tests.

Why loopback and synthetic

Everything runs on 127.0.0.1 with made-up data, so a run is repeatable, safe to share and never touches a real service. The cost is stated: a fixture proves a mechanism, not your production.

Why numbers come from files

On-screen results are copied from each fixture's evidence.json. Scenes that could not be executed are labeled conceptual on screen.

What this is, and what it is not

Exists today

  • 28 narrated films with captions, thumbnails and hero images
  • A runnable fixture and node:test suite behind each one that executes code
  • Three article versions per episode: engineers, buyers, plain language
  • Three launch packages, three launch films and three quizzes

Does not claim

  • It is not an audit, a certification or a finding about any real product
  • A passing fixture does not prove your system is safe
  • Some scenes are conceptual illustrations and say so on screen
  • There is no roadmap, and nothing here is promised

Run a fixture yourself

Node 22 or newer is the only requirement for this fixture. No install step, no network.

macOS and Linux

git clone https://github.com/mizcausevic-dev/web-reality-checks.git
cd web-reality-checks/fixtures/ep01-authz
node --test
node demo.mjs

Windows PowerShell

git clone https://github.com/mizcausevic-dev/web-reality-checks.git
cd web-reality-checks\fixtures\ep01-authz
node --test
node demo.mjs

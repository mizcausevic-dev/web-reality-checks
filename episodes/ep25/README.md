# EP 25 — Your Backup Says 'Successful.' Can You Actually Restore It?

**Central idea.** Creating a backup artifact and recovering usable application data are different outcomes; only a restore plus validation tells you which you have.

## What this fixture is
- `fixtures/ep25-restore-tests/` — a synthetic SQLite shop (12 customers, 40 orders, `user_version` 3) with foreign keys ON for application connections, backed up with Python's `sqlite3.Connection.backup()` (Online Backup API) from a quiescent WAL-mode source.
- The backup is copied to a fresh temp path and validated: `integrity_check` (`ok`), `foreign_key_check` (no rows), schema version, tables, record counts, selected known values, and the application's real order-total query.
- The source is never overwritten or opened by the validator; the restored copy holds the backup's data, not later source writes (source 41 orders, backup 40).
- Deliberately invalid artifacts (non-SQLite file, orphan order with unchanged counts, wrong value with unchanged counts, missing table, wrong schema version) fail with a structured result and never crash validation.
- Do-not-copy-only-the-main-file: a control shows a main-file-only copy of a live WAL database fails validation.

## Evidence
- Executed: `node --test fixtures/ep25-restore-tests/test.mjs` → `# tests 16 / # pass 16 / # fail 0`.
- Executed: `node fixtures/ep25-restore-tests/demo.mjs` → `evidence.json`: backup ok (20480 bytes, 5 pages); good backup passes all eight checks; orphan artifact passes `integrity_check` and counts (12 / 40) but fails `foreign_key_check`; wrong-value artifact passes integrity, foreign-key and count checks but fails `known_values` and `order_totals_query` (Hugo Placeholder 19911 expected, 20011 found); non-SQLite file fails at `restore_open` with `DatabaseError: file is not a database`.
- Measured on this machine only: backup and restore durations (about a millisecond on a 20 KB file) are in `evidence.json`; they are not shown in the video and are not recovery-time claims.
- Predicted / Blocked: none. Narration audio and MP4 are not generated by this build step; `video/src/episodes/ep25/timeline.json` was produced with `--no-audio` (estimated timing) and must be rebuilt from real audio.

## Accuracy items and where they appear
- integrity_check does not replace foreign_key_check: scenes `checks` and `fail` (narration + on-screen "Why both checks", card B).
- Record counts alone do not establish recovery: scenes `values` and `fail` (cards B and C keep 12 / 40).
- Unmistakably invalid fixture, no assumed truncation error: scene `fail`, "built by explicit edits, not by random truncation".
- Validation failure handled without crashing: scene `fail` card A (structured result, exit 1).
- Restore duration: not shown in the video.
- No recovery-time or recovery-point guarantees; external files, object storage, secrets, infrastructure out of scope: scene `end`.
- Restored copy contains the backup's data, not later source writes: scene `restore` (41 vs 40 orders).
- Online Backup API, not a main-file copy of a live WAL database: scene `restore`.

## Limitations
- One tiny synthetic database; real corruption modes are not simulated.
- Scene timings follow the narration audio proportionally (heuristic alignment, not forced alignment).
- All on-screen numbers are copied from `evidence.json`; the 12-row totals table repeats the validator's `order_totals` output.
